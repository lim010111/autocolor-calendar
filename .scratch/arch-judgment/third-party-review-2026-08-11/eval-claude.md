## 2. 핵심 결함·리스크

**[높음] 판정 기준을 스스로 못 지킨 채 Accepted.** 초안 `1-...verdict-draft.md:23-24` 가 교체 조건을 "두 런 모두 밴드 밖 승리 **AND** hard 슬라이스에서 나쁘지 않을 것" 으로 못박았고, 같은 문서 `:202-206` 은 "hard 슬라이스 검증: 436건 채굴 완료 — 큐레이션·라벨 후 **최종 확정 전 확인 필요**" 라고 미완으로 남겨두었다. ADR-0008 에는 이 잔여 항목이 한 줄도 없고 Status 는 Accepted (2026-08-11) 다. 낙폭: 나중에 hard 슬라이스에서 C 가 A 에 밀리는 것이 드러나도 되돌릴 지점이 문서상 존재하지 않는다.

**[높음] 채택 전 검증으로 적힌 서드파티 리뷰가 아직 존재하지 않는다.** ADR `:49-51` 은 "채택 전 검증 2건: 요소 존재론 리뷰 … 와 **서드파티 적대 리뷰 1회**" 라고 완료형으로 쓰고 경로도 달지 않았다. 프로젝트 보드는 같은 건을 "Codex 리뷰 결과 회수·반영만 남음" 으로 적고 있다. 게다가 회수 후 ADR 본문에 반영하겠다는 계획은 `docs/adr/README.md:48-50` 의 "ADR 본문은 결정 시점 trade-off 를 그대로 박제한다 … 본문을 편집하지 않고 새 ADR" 규칙과 정면 충돌한다. 낙폭: ADR 이 검증 기록이 아니라 사후 편집 대상이 되어 아카이브로서의 신뢰가 사라진다.

**[높음] "내일 verified 가 되살아난다" 는 코드가 막고 있다.** 초안 `:76-78` 은 declared 오프의 정당화로 "예시가 쌓이면 그 규칙만 T_verified=0.30 경로로 Stage 1 이 되살아난다 — 임베딩 인프라는 그대로 자산" 이라고 썼다. 그런데 `src/services/stage1.ts:138` 의 풀 질의는 `SELECT DISTINCT ON (rule_id)` 로 규칙당 최고 씨앗 1개만 올리고, `:99-100` 은 `grade = gradeOf(best.seedType)` 로 등급을 **풀 전체 최고 씨앗** 에서 뽑는다. 규칙 X 의 name 씨앗이 0.62, example 씨앗이 0.58 이면 example 은 아예 후보로 올라오지 못하고 등급은 declared 로 확정된다 → declared 오프 = 그 규칙의 verified 경로도 같이 꺼진다. 존재론 리뷰 `2-...:55-57` 이 이 masking 을 정확히 발견해 놓고도, 초안·ADR 은 그 발견을 "씨앗 행 거취는 나중에 판정" 으로 미루면서 부활 서사를 그대로 유지했다. 낙폭: 8/28 이후 예시가 쌓여도 Stage 1 은 상당수 규칙에서 영구 침묵하고, "가역적·자산" 이라는 인프라 유지 근거가 무너진다.

**[높음] `keywords.min(0)` 완화 근거가 측정된 적 없는 상태에 기대고 있다.** 존재론 리뷰 `:50-52` 와 ADR `:101-105` 는 "LLM 단독에서 name 만으로 동작 **실측**" 을 근거로 min(1) 완화를 밀고 있다. 그러나 `evals/arch-judgment/build_fixtures.py:89-91` 의 `build_keywords` 는 `richness == "min"` 일 때 `return [display_name]` 이다 — 즉 min 조건은 프롬프트에 `keywords: ["<이름>"]` 을 항상 보낸다. `keywords: []` 는 8조건 어디에도 없다. 완화가 만들어낼 신규 온보딩 상태는 전 측정 범위 밖이며, 최대 지렛대라던 desc +0.077 도 `keywords=[name]` 위에서 잰 값이다. 낙폭: 완화 배포 직후 신규 사용자 기본 자세가 미측정 영역으로 이동, prod 오분류 재발 시 원인 귀속 불가.

**[높음] 캐시 스펙 부재가 배포 순서 제약을 무력화한다.** ADR `:70-72` 의 캐시 키는 `(제목 × 규칙셋 + 프롬프트 버전)` 이고 무효화 목록에 **판정 정책 버전이 없다.** 강제된 순서가 캐시 → 2표이므로, 캐시가 먼저 도는 기간의 1표 판정이 그대로 동결되고 §5.4 래칫과 결합해 영구화된다 — 2표가 막으려던 오적용이 바로 그 창에서 굳는다. 반대 방향도 있다: 무효화 트리거에 "description 편집" 이 들어 있는데, 묶음 1번(description 도입)은 정의상 **전 사용자가 규칙을 편집하게 만드는 기능** 이다. 즉 캐시가 전면 무효화된 직후 cold resync 가 1.9배율로 돌아, 캐시가 흡수해 준다던 쿼터 스파이크가 그대로 발생한다.

**[중간] 쿼터 초과 논증의 산술이 틀렸다.** ADR `:74-76`: "2표는 콜을 1.54배로 늘리는데 … 관측된 resync 스파이크(116콜/일)를 환산하면 … 초과한다(~220콜)". 116 × 1.54 = 179 로 200 미만이다. 220 은 Consequences `:89` 의 "현행 대비 ~1.9배"(= 1.54콜/케이스 ÷ 현행 ~0.8콜/케이스)를 써야 나오고, 그 증가분의 대부분은 2표가 아니라 declared 오프에서 온다. 낙폭: 제약을 검산한 사람이 179 를 얻고 "순서 제약 불필요" 라고 결론내린다.

**[중간] 헤드라인 +0.566 은 prod 분포가 아니다.** `score.py:33-37` 의 8조건 중 5개가 `SPARSE`(카테고리 6/3/2개), 2개가 합성 교차언어(en 이름 × ko 제목)이며 `tally` 는 전 케이스를 등가중 평균한다. 실사용자는 자기 카테고리 전량이 목록에 있는 ko-11 상태다. 두 문서 모두 이 수치를 "최종 자세 실측" 으로 제시하는데, 실제로는 임의 조건 믹스의 평균이다. 낙폭: 출시 후 prod 재채점(트리거 1)이 +0.566 을 재현 못 할 때 회귀로 오독된다.

**[중간] 불확실성 정량화가 런간 편차 하나뿐이다.** `evals/arch-judgment/` 전체에 bootstrap / CI / paired-test 가 하나도 없다(해당 어휘 grep 0건). ±0.015 밴드는 **LLM 비결정성만** 담고 케이스 표집 변동은 담지 않는다. 게다가 8조건은 동일한 311개 제목의 상관 반복인데 n=2488 처럼 취급된다. 유효 n 을 311 로 보면 페어드 델타의 표준오차가 C−A = 0.034 와 같은 자릿수로 올라온다. desc 의 +0.05 는 견디겠지만 **declared 오프 판정 자체는 이 구분에 민감하다.**

**[중간] description 효과에 저자 편향이 걸려 있을 수 있다.** 골드셋 311건은 운영자 본인 캘린더이고, wave-3 의 설명 11개(`_local/arch-judgment/rule-descriptions.json`)도 같은 사람이 **그 제목들을 이미 알고** 쓴 것이다. 신규 사용자가 자기 일정을 보지 않고 쓰는 한 줄과 같은 값을 낸다는 보장이 없다. 초안 「한계」 5항목·ADR 재판정 트리거 4항목 어디에도 이 한계가 없다.

**[중간] 측정된 desc 는 "프롬프트가 모르는 필드" 였다.** 초안 `:125` 이 "v8 시스템 프롬프트 무변경(필드만 추가)" 을 순수 데이터 효과의 근거로 삼았다. 그런데 채택 비용에는 "시스템 프롬프트에 필드 문서화 여부 포함" 이 들어 있다 — 문서화하면 +0.05 는 재측정 대상이 되고, 문서화하지 않으면 `src/services/llmClassifier.ts:221-231` 이 examples 에 대해 세워둔 규율(프롬프트가 문서화한 버전에만 필드를 보낸다)을 description 에서만 깨는 셈이다. 어느 쪽이든 지금의 숫자는 그대로 살아남지 못한다.

**[중간] 이름 충돌 + 미측정 필드.** `buildPrompt` 는 이미 `event.description` 을 보낸다(`llmClassifier.ts:265`). 여기에 `categories[].description` 이 붙으면 한 JSON 안에 동명 필드가 둘이 되는데, 평가 픽스처는 제목만 채워 `event.description` 이 빈 문자열이라 이 충돌은 한 번도 실행되지 않았다. 더 나쁜 건 ADR 재판정 트리거 4 "프롬프트가 summary 외 필드(description/location)를 소비하게 될 때" — **이미 소비 중이라 영원히 발화하지 않는 트리거다.**

**[중간] verified 칠하기만 무검증 경로로 남는다.** 2표 게이트는 LLM 1차 판정에만 걸린다(ADR `:68-69`). declared 오프 이후 Stage 1 이 칠할 수 있는 유일한 길인 verified 는 바가 가장 낮고(0.30) 측정된 적이 없는데(초안 한계 5) 재확인 없이 즉시 칠한다. 즉 "측정돼서 나쁜 걸로 밝혀진 레그" 를 끄면서 "측정 안 된 레그" 를 유일한 무게이트 페인트 경로로 남겼다.

**[낮음] 헤드라인 근거 숫자가 파(wave) 간에 섞였다.** ADR `:36` 의 "오적용 10.5→8.6%" 는 wave2 의 10.4→~8.0(desc 없음)도 wave3 의 ~10.1→8.6(desc 있음)도 아니다.

**[낮음] 증거 사슬 일부가 복구 불가.** 존재론 리뷰 `:70-72`: "서브에이전트 전문은 세션 로그에만 있음". ADR 이 채택 전 검증으로 인용하는 문서의 원자료가 사라졌다. 또 두 문서의 `_local/arch-judgment/...` 표기는 실제 경로 `evals/embedding-eval/_local/arch-judgment/...` 와 달라 재현 지시가 그대로는 안 먹는다.

**[낮음] 정본 문서 미갱신.** `src/AGENTS.md` 의 "Stage 1" 절은 여전히 declared 배정을 live invariant 로 기술하고, `docs/adr/README.md:43-46` 은 충돌 시 그쪽이 우위라고 못박는다. ADR 은 이 갱신 의무를 후속 항목으로 적지 않았다.

## 3. 놓친 대안

**디코딩 파라미터 / logprobs.** `callOpenAi`(`llmClassifier.ts:400-424`)는 temperature·seed·logprobs 를 아무것도 보내지 않는다. 2표는 모델 확신도를 **재표집으로 추정하는 가장 비싼 방법** 이고, logprobs 는 1콜로 같은 신호를 준다. 모델 계열 제약으로 불가하다면 그 사실이 기각 근거로 기록됐어야 하는데, 31개 후보 어디에도 디코딩 파라미터 축이 없다.

**재확인 콜의 프롬프트 축소.** 확인 단계는 후보 2개만 두고 물으면 되는데 3K 토큰 전체를 재전송하는 설계를 전제했다. 지금 쿼터는 콜 수 기준이라 절약이 안 되지만, 그렇다면 대안은 "쿼터를 토큰/비용 기준으로 재정의" 이며 이것이 캐시→2표 순서 제약보다 훨씬 단순하다.

**사람 확인을 게이트로.** 목적함수가 오적용:미배정 = 3:1 이면, 확신 낮은 케이스를 칠하지 않고 Instant Feedback UI 로 넘기는 것이 콜을 1.9배로 늘리는 것보다 싸고 확실하다. ec#05 경로가 이미 있는데 후보 목록에 없다.

**description 을 사용자에게 받지 않는 경로.** 최대 이득 지점이 "온보딩(키워드 없음)" 인데, 그 시점 사용자는 선택 입력을 가장 안 쓴다. ec#06(히스토리 기반 규칙 제안)으로 초안 설명을 자동 생성하는 안이 검토되지 않았다 — 채택률 0 이면 +0.05 도 0 이다.

**조건 등가중 대신 prod 분포 가중,** 그리고 이미 보유한 4언어 데이터셋(`evals/datasets/{lang}/classification.json`)으로 n=1 한계를 부분 완화하는 안. 단일 사용자 한계를 "상대 순위는 구조적" 이라고 선언만 하고, 보유 자산으로 반증 시도를 하지 않았다.

## 4. 제3자라면 멈췄을 지점

**Accepted 도장을 찍은 순간.** hard 슬라이스 미검증 + 서드파티 리뷰 미회수 상태에서 Status 를 Proposed 아닌 Accepted 로 올린 것은 문서 규율 위반이자, 이후 "본문 편집" 계획과 결합해 ADR 을 사후 합리화 문서로 만든다.

**"실측" 이라는 단어를 min(0) 완화에 붙인 문장.** `keywords: []` 는 한 번도 모델에 보낸 적이 없다. 여기서 멈추고 wave-4 한 조건만 더 돌렸으면 끝났을 일이다.

**캐시를 스펙 없이 4개 묶음에 넣은 것.** 키 구성·정책 버전·TTL·원문 제목 저장 여부가 전부 미정인 구성요소가 배포 순서 제약의 **전제** 가 되어 있다. 프라이버시(§12) 미결이라고 스스로 적어놓은 항목을 채택 결정에 넣으면 안 된다.

**verified 를 "조건부 유지" 로 넘긴 판단.** masking 때문에 유지가 실효를 못 내거나(부활 안 함), 실효를 내는 순간 유일한 무게이트 페인트가 되거나 — 둘 중 하나인데 어느 쪽인지 결정하지 않은 채 declared 를 껐다.

**n=1 데이터로 상수까지 판정하고 "상대 순위는 구조적" 이라 단정한 부분.** 골드셋·설명·이름 번역 감수가 모두 같은 사람에서 나왔다. 이 상관을 인정하는 문장이 세 문서 어디에도 없다.
